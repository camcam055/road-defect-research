3.0 Methodology

This section outlines the method that was used to develop and train the AI-based pavement defect detection system. This section includes dataset selection, data preparation, model training and real-world data collection to improve the model performance under New Zealand road conditions.

3.1 Data Sources

To establish a baseline model for this project, the RDD2022 dataset was obtained from Dataset Ninja. This dataset was chosen as it had many labelled road defects varying across multiple countries including Japan, India, the Czech Republic and others. This dataset provided a range of pavement conditions, lighting environments and defect types. This is important for training an AI model as variation is required to establish a strong baseline model.

In addition, the dataset reduces the need for manually labelling photos. This is because the dataset comes with labels for each photo, allowing an efficient conversion into YOLO format. This then made it possible to establish a strong baseline model before adding in locally collected New Zealand data.

3.2 Data Preparation

In the RDD2022 dataset, the labels had to be converted from a JSON format into a YOLO text format before training the AI. This involved writing a script (convert for yolo.py) to be written. The script works by first determining the batch size, which is the number of images to be including in each batch. Then, to reduce bias, the script randomly selects labels from the folder that have a matching image. This is because analysis during earlier testing showed that some images don’t have labels or labels are empty. Then the script converts those labels from a JSON format into the YOLO text format. Then the script splits the labelled data into a train and a Val folder. The split is 0.2, which means 80% of the labelled data will go into a train folder and 20% into a Val folder. Once that is completed the script then creates a YAML file. The YAML tells the YOLO model where the data is.

The New Zealand data the data will be manually annotated in CVAT and then used to train the AI model. Once the mAP50 is above 0.75, the AI will annotate the data automatically which can save time and effort. However, to make sure that the labels are correct, manual inspection will be carried out to determine if the labels are correct. If there are any wrong labels, they will be redone manually to make sure that the AI is not trained on incorrect data.

The script was then executed using the macOS terminal with a Python command.

3.3 Model Training

A YOLO (You Only Look Once) object detection model was used to train the pavement defect detection AI. The model was trained using transfer learning from pretrained weights. Transfer learning enabled the model to reuse previously learned patterns to improve the reliability of defect detection.

The model development followed a version-based approach. Version 1 consisted of the RDD2022 dataset, which was used to establish the training pipeline, evaluate initial performance and establish a strong baseline model for New Zealand pavements.

Initial training was conducted locally on a MacBook Air M2 using the computer's CPU. This was done to validate the dataset structure and make sure that the model configuration was working as expected and improving over time. However, due to the slow speed of training, thermal limitations and the increasing number of photos in each batch increased, training runs were often completed overnight. The MacBook was kept turned on using the caffeinate command in Terminal.

To improve training efficiency, the training workflow was moved onto a cloud-based GPU environment using Google Colab. Early runs using the small AI model utilised a Tesla T4 GPU. As further improvement was needed to support New Zealand data, the model was upgraded to the large YOLO model. This increased the computational demand significantly. To maintain practical training times, higher-performance GPUs were utilised. This included GPUs such as the NVIDIA A100 for training the large model and the H100 GPU. The extra-large YOLO model was also briefly tested on the NVIDIA H100 GPU to see if increasing the model size could further improve the baseline model.

Throughout training, progress was tracked in an Excel spreadsheet for each run by recording details and figures for each run. This included training time, number of training and validation images, number of epochs, precision, recall and mAP50. This allowed model performance to be visualised and compared across each batch. In addition to this spreadsheet, YOLO training outputted training performance metrics in a CSV file and in different graphs to evaluate the model performance.

The model was trained for 60 epochs. An epoch refers to one complete pass through the entire training dataset during the training process, allowing the model to update and learn more efficiently. The image size of 640 pixels was selected to ensure adequate detail for defect detection without significantly increasing training time. The YOLOv8L model was selected to detect defects due to its balance between accuracy and efficiency, making it suitable for training on local hardware and cloud-based environments.

The AI was executed using the macOS terminal with a Python command.

3.4 Data Collection in New Zealand

Because the original dataset (RDD2022) did not include New Zealand-specific pavement environments, the model required further training on local roads in New Zealand to improve accuracy and generalisation. In addition, the model needed to be tested in real-world conditions to make sure that the training from the RDD2022 dataset served as a baseline model.

Version 2 expanded on Version 1, where the model was trained on a smaller set of targeted photos manually captured using an iPhone 13 Pro. These images were taken to provide the AI with specific defect types and provide higher-quality, close-up examples of pavement defects to fill in gaps in the dataset and to train the AI on New Zealand pavements.

Version 3 involved the introduction of a vehicle-based data collection approach where an iPhone 13 Pro was mounted on the windscreen. The iPhone was mounted using a Ulanzi ZJ01 Extendable Magnetic Suction Cup, which provided a secure, stable mount and enabled hands-free operation while running a dashcam app to record road footage and GPS data during normal driving conditions. This mount allowed stable, consistent, and safe data collection which is required for training and testing the AI model. It also enabled the capture of real-world conditions while driving such as different surface types, angles and varying lighting conditions. This provided the model with real-world conditions that it is intended to operate in.

Testing for Version 3 was on a preselected route that contained rural roads, a motorway and urban roads. This was to check consistency across different road types and check how the model was improving over time.

In the proposal, a GoPro was initially considered for data collection due to its flexible mounting options and video recording features including GPS data. However, the model was a GoPro Hero 5 which was released about 10 years ago and was therefore considered outdated for this project. It was also less suitable due to the wide-angle lens which produced a field of view that was too wide for capturing road defects accurately. As a result, the iPhone 13 Pro was selected as the preferred device for capturing road defects in New Zealand pavements.

3.5 Model validation

To be able to assess how well the AI model has performed, evaluation metrics are needed. These metrics were recorded in an Excel spreadsheet and a CSV file from each training run and show how well the model can detect and classify pavement defects. There are many types of metrics; however, the main ones of are precision, recall and mAP50.

These metrics were used to compare performance between the batches, identify trends and determine whether overfitting was occurring. This allowed improvements in detection accuracy and overall model performance to be assessed over time.

3.6 Workflow development

To make it easier for users to scan road footage and review detected pavement defects, a simple desktop workflow was developed which combines image processing, AI defect detection using the latest model, GPS data, mapping data such as traffic data and soil properties, and reporting into one system. This was done to make it easier for a user to film a section of road, load it into the system and obtain results quickly without having any knowledge of Python or scripting. This workflow was developed using python. This is because Python allows AI model integration, data processing, GIS mapping, and automated report generation.

Once, a section of road is filmed, the user first saves it to a folder, The user opens the .command file, which launches Terminal and starts a Python-based road defect detector application using Tkinter, which is a built-in Python GUI library. Tkinter was used to create an application window where users can select the road footage. Once the user clicks “Run AI”, the user then selects either a folder of images or video footage. If a video is selected a macOS command called FFmpeg which extracts 1 image frame per second which reduces the total workload for the computer and reduces duplicate images while still covering all the road. Each frame that has been detected with a defect then gets a GPS timestamp based on its position within the video. When a folder of photos is selected, the latitude and longitude are extracted from each image and then matched using the image filename. The GPS information is then stored in a JSON file for later use for the mapping and reporting.

Then, once that is all done, then the script runs the YOLO pavement defect detection model. The model then scans through all images, and then saves the images with annotated images, label files and confidence values for each inspection run.

Then there is a preliminary maintenance recommendation for each type of defect. For example, a longitudinal crack will be assigned a recommendation for crack sealing and/or monitoring. However, in the future this could be done with a local AI model instead. These recommendations are used to support maintenance decision-making rather than to replace a proper engineering inspection. These recommendations may be changed using the PDI calculations in Section 3.7.

Then, once everything is done, an interactive map is generated using Folium, which is another Python library which is used to create an interactive web-based map using geographic data such as latitude and longitude. This was used in this project because it allows GPS-referenced points, traffic data and soil condition information to be displayed as an interactive map. A PDF report is also generated and includes a summary of each detected defect, type of defect, GPS coordinates, confidence values, and recommended actions.

There is a master map which includes all defects and has different layers for traffic data and soil conditions. This is useful because users can compare where defects are found in relation to traffic volumes and soil conditions. For example, a section of road which has a high number of defects can also display a high traffic volume and poor soil conditions which may lead to more defects. In the future, it may be possible to add another layer which displays when that road was last repaired or built and have a local AI reason over the map.

3.7 PDI calculations

To assess the general condition of the pavement condition, the surveyed road is split into 50-metre sections. The AI detections are then matched using their GPS coordinates to each 50-metre section. Then the total number of defects within each 50-meter section is used as the PDI value.

Each defect counts as 1 regardless of its type. This keeps it simple and easy to calculate. For example, if the AI see within one 50-meter section 2 potholes, a lateral crack and a patch of alligator crashing, the total PDI value for that 50m would be 4.A higher PDI value would then represent a greater concentration of pavement defects within that section.

The PDI value is then shown visually on the map through a continuous colour scale. Sections with a low PDI score will show green, while sections with higher scores will change to orange and then to red, showing sections with the highest concentration of pavement defects. This makes it easier to quickly identify areas of the road that may require further inspection or maintenance.

Figure 10: Continuous map display

The system also prevents the same defect from being counted multiple times when it appears in several consecutive video frames.

Future versions of this PDI system could use a large language model (LLM) with image analysis capabilities to further assess each detected pavement defect. This will be done after the AI detection model identifies a defect; then the image will be passed to an LLM model. The LLM model will be able to estimate the approximate size of the defect and provide a severity score based on the visible details such as width, length, depth, and surface deterioration. The LLM is different to the defect detection AI because the defect detection AI finds the defects while the LLM analyses each detected defect in more detail.
